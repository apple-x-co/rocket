> version: 1.1.0

## Context

- Current branch: !`git branch --show-current`
- Remote branches: !`git branch -r`
- Upstream: !`git rev-parse --abbrev-ref --symbolic-full-name @{u} 2>/dev/null`

**重要**: Context のブランチ情報はそのまま利用してよい（再取得しない）。ただし PR の**内容**の生成には、ステップ3で取得する差分のみを使用すること。

## Your task

現在のブランチから GitHub の Pull Request を作成します。ブランチ一覧から選択可能なマージ先を提示し、コミット内容を分析して適切な PR タイトルと本文を生成します。

### ステップ1: 事前チェック

1. **現在のブランチ確認**:
    - Context の `Current branch` を使用（再取得しない）
    - `main` または `master` または `develop` の場合は「デフォルトブランチからは PR を作成できません。feature ブランチに切り替えてください」と通知して終了

2. **リモートとの同期確認**:
    - Context の `Upstream` を使用（再取得しない）
    - 空の場合は「リモートブランチが設定されていません。`git push -u origin <branch-name>` で push してください」と通知して終了

### ステップ2: マージ先ブランチの選択

1. **利用可能なブランチ一覧を取得**:

   Context の `Remote branches`（`git branch -r` の出力）を処理対象とする（再取得しない）:
    - `origin/` プレフィックスを削除
    - `HEAD` を除外
    - 現在のブランチを除外
    - 重複を削除
    - ソート


2. **候補ブランチの優先順位付け**:
    - `develop`, `main`, `master` を優先的に表示
    - その他のブランチもアルファベット順で表示
    - 現在のブランチは除外

3. **`AskUserQuestion` でマージ先を選択**:
    - `question`: "PR のマージ先ブランチを選択してください"
    - `header`: "Base branch"
    - `multiSelect`: `false`
    - `options`: ブランチ一覧を配列で指定
        - `develop` が存在する場合は最初に配置（推奨）
        - 各 `label` にはブランチ名
        - 各 `description` には「推奨」「本番」「メインブランチ」などの説明を付与
    - デフォルト選択: `develop` が存在する場合は `develop`、なければ `main` または `master`

### ステップ3: 既存 PR のチェック・差分分析（統合）

**🚨 最重要制約 🚨**:
このステップでは、**以下のコマンドを実行して、その出力のみ**を使って PR 内容を生成します。
**それ以外の情報源は一切使用禁止**です。

**既存PRの確認とコミット差分の取得を1回のコマンド実行にまとめる**。`<現在のブランチ名>` / `<ベースブランチ>` にはステップ1・2で確定した値をリテラル文字列として代入する（shell substitution 不可）。

```bash
echo "=== EXISTING_PR ==="
gh pr list --head <現在のブランチ名> --base <ベースブランチ> --state all --json number,title,state,url
echo "=== COMMITS ==="
git fetch --no-tags --quiet origin <ベースブランチ> && git log origin/<ベースブランチ>..HEAD --pretty=tformat:"### %h %s%n%b" --reverse
echo "=== FILES ==="
git diff origin/<ベースブランチ>..HEAD --name-status
echo "=== NUMSTAT ==="
git diff origin/<ベースブランチ>..HEAD --numstat
echo "=== STAT ==="
git diff origin/<ベースブランチ>..HEAD --shortstat
```

**`gh` が認証エラーを返した場合**: 「`gh auth login` で認証してください」と通知して終了

**読み取りルール**:
- **既存 PR** = `EXISTING_PR` 区画のうち `state` が `OPEN` または `DRAFT` のもの（`MERGED` や `CLOSED` は除外）。フィルタリング後に空配列になった場合は既存 PR なし
- **コミット数** = `COMMITS` 区画の `### ` で始まる行数
- **変更ファイル一覧と新規/更新/削除** = `FILES` 区画の `A` / `M` / `D`（プロジェクトルートからの相対パス）
- **ファイルごとの追加・削除行数**（CodeRabbit AI風テーブル用） = `NUMSTAT` 区画
- **変更ファイル数 / 追加・削除行数（合計）** = `STAT` 区画の `N files changed, N insertions(+), N deletions(-)`

**例1: 差分が2コミットの場合**
```
### abc1234 feat: 機能Aを実装

機能Aの詳細な説明

### def5678 fix: バグ修正

バグ修正の詳細
```
→ **この2つのコミットのみ**が PR の対象。過去の大規模変更（機能B実装など）は**含まれていない**ので PR に書かない。

**例2: 差分が1コミットの場合**
```
### abc1234 refactor: コードリファクタリング

不要なコードを削除
```
→ **この1つのコミットのみ**が PR の対象。

**差分が0コミットの場合**: 「ベースブランチとの差分がありません」と通知して終了

**既存 PR が見つかった場合の処理**:

**`AskUserQuestion` で対応方法を選択**:
- `question`: "このブランチから <ベースブランチ> への PR が既に存在します (#番号)。どうしますか？"
- `header`: "Existing PR"
- `multiSelect`: `false`
- `options`:
  ```json
  [
    {
      "label": "既存の PR を更新する（推奨）",
      "description": "新しいコミットを既存の PR に追加します。タイトルと本文は更新されません。"
    },
    {
      "label": "既存の PR のタイトル・本文を編集する",
      "description": "既存の PR のメタデータを更新します。"
    },
    {
      "label": "既存の PR を無視して新規 PR を作成する",
      "description": "既存の PR はそのままにして、新しい PR を別途作成します（通常は推奨されません）。"
    },
    {
      "label": "既存の PR をブラウザで確認する",
      "description": "既存の PR を開いて内容を確認します。"
    },
    {
      "label": "キャンセル",
      "description": "何もせずに終了します。"
    }
  ]
  ```

**選択に応じた処理**:

**a) 既存の PR を更新する（推奨）**:

`state` と `url` は `EXISTING_PR` 区画の取得結果から読み取る（再取得しない）。`<現在のブランチ名>` にはステップ1で取得したブランチ名をリテラル文字列として代入する（shell substitution 不可）。

- `EXISTING_PR` の `state` が `MERGED` または `CLOSED` の場合:
    - 「この PR は既にマージ/クローズされています。新規 PR の作成に切り替えますか？」と確認
    - Yes → 新規 PR 作成フローに進む
    - No → 処理を終了

- `state` が `OPEN` または `DRAFT` の場合:
  ```bash
  # 最新のコミットをリモートに push
  git push origin <現在のブランチ名>
  ```
    - 「既存の PR に最新のコミットが反映されました」と報告
    - `EXISTING_PR` の `url` を表示

**b) タイトル・本文を編集する**:

- `EXISTING_PR` の `state` が `MERGED` または `CLOSED` の場合:
    - 「この PR は既にマージ/クローズされています。マージ済み/クローズ済みの PR は編集できません」と通知して終了

- `state` が `OPEN` または `DRAFT` の場合:
    - 差分は取得済みのため、そのままステップ4（変更の分類）・ステップ5（PR 候補生成）に進む
    - 選択された内容で既存 PR を更新:
      ```bash
      gh pr edit <PR番号> --title "<新しいタイトル>" --body "<新しい本文>"
      ```

**c) 既存の PR を無視して新規 PR を作成する**:
- 差分は取得済みのため、そのままステップ4（変更の分類）に進む
- 新規 PR 作成フローを実行
- 注意: 同じブランチから複数の PR が存在することになります

**d) ブラウザで確認**:
```bash
gh pr view <PR番号> --web
```
- 処理を終了

**e) キャンセル**:
- 「処理をキャンセルしました」と報告して終了

**既存 PR が見つからなかった場合**:
- そのままステップ4（変更の分類）に進む

### ステップ4: 変更の分類と PR 内容の生成ルール

**変更内容の詳細分析（CodeRabbit AI風のテーブル用）**:

`NUMSTAT` 区画の出力例:
```
10      5       src/Module/FeatureA.php
50      0       src/Module/NewFeature.php
15      3       templates/feature/new.html
```
→ 各ファイルの追加行数と削除行数がわかる

**変更の分類と説明の生成**:

コミットメッセージとファイルパスから、プロジェクトの特性に応じて変更をカテゴリ化する。

**カテゴリ化の基本原則**:
1. **ファイルの役割や変更の目的でグループ化**
    - 同じ機能や目的に関連するファイルをまとめる
    - ディレクトリ構造を参考にする
    - コミットメッセージから関連性を判断する

2. **カテゴリ名は変更の内容を反映**
    - 「何を」変更したかを明確にする
    - プロジェクト固有の用語を使用してOK
    - 技術的に正確な表現を使う

**カテゴリ分類の例**（プロジェクトに応じて適切なカテゴリを選択）:

**一般的なカテゴリ**:
- **新機能の追加**: 新規機能に関連するファイル群
- **バグ修正**: 特定のバグ修正に関連する変更
- **リファクタリング**: コード構造の改善
- **パフォーマンス改善**: 速度やリソース使用の最適化
- **セキュリティ修正**: セキュリティ関連の変更
- **依存関係の更新**: ライブラリやパッケージの更新

**アーキテクチャ・設計**:
- **インターフェース/抽象化の追加**: 抽象レイヤーの導入
- **実装クラスの更新**: 具体的な実装の変更
- **設計パターンの適用**: デザインパターンの導入
- **依存性注入の設定**: DIコンテナやモジュールの設定

**レイヤー別**:
- **プレゼンテーション層**: UI、ビュー、テンプレート
- **アプリケーション層**: コントローラー、ユースケース
- **ドメイン層**: ビジネスロジック、エンティティ
- **インフラストラクチャ層**: データベース、外部API連携
- **フロントエンド**: CSS、JavaScript、HTML
- **バックエンド**: サーバーサイドロジック

**ファイルタイプ別**:
- **ソースコード**: 実装ファイル
- **テストコード**: ユニットテスト、統合テスト
- **設定ファイル**: YAML、JSON、環境変数
- **ドキュメント**: README、API仕様書
- **ビルド/デプロイ**: CI/CD、ビルドスクリプト

**各カテゴリについて**:
1. カテゴリ名（Cohort）を決定
    - コミットメッセージから変更の性質を抽出
    - ファイルパスからディレクトリ構造を理解
    - 関連する変更を論理的にグループ化
2. 関連ファイルをグループ化
    - 同じカテゴリに属するファイルをまとめる
    - 多すぎる場合は適切に分割（1カテゴリあたり3-5ファイル程度）
3. コミットメッセージから変更概要を生成
    - 各カテゴリが何を達成するかを説明

**変更概要の生成ルール**:
- **コミットメッセージを主な情報源として使用**
- 技術的な詳細を含める（追加された機能、変更された振る舞い、依存関係の変更など）
- 変更の理由や目的を明確にする
- プロジェクト固有の用語（クラス名、関数名、モジュール名など）を使用してOK
- 2-4文程度の説明文にまとめる

---

**PR 内容の生成ルール**:

**使用してよい情報（ステップ3で取得したもののみ）**:
- ✅ `COMMITS` 区画で取得したコミットメッセージとコミット本文
- ✅ `FILES` 区画で取得した変更ファイルのパス
- ✅ `COMMITS` 区画から数えたコミット数
- ✅ `STAT` 区画から読み取った変更ファイル数
- ✅ `NUMSTAT` 区画で分析した変更の分類と統計

**使用禁止の情報**:
- ❌ Context セクション
- ❌ `git log --oneline -10` などの直近のコミット
- ❌ `git status` や作業ディレクトリの状態
- ❌ Claude の記憶、推測、想像
- ❌ ステップ3の出力に含まれていない情報

**確認方法**:
PR 本文に記載する全ての情報（コミット内容、ファイル名、機能名、変更内容）が、
**ステップ3の出力から直接確認できる**ことを確認してください。

**具体例**:
- もし `COMMITS` 区画に「formrun 移行」というコミットがない → PR に「formrun 移行」を書かない
- もし `FILES` 区画に `src/repository/user_repository.py` がない → PR に `src/repository/user_repository.py` を書かない
- もし `COMMITS` 区画が「エラー画面を実装」の2コミットのみ → PR には**エラー画面の実装のみ**を書く

---

**🚨 重要 🚨**:
このステップを正しく実行しないと、**PR に含まれない過去の作業内容**が混入します。
`COMMITS` 区画の出力を**必ず最初に確認**し、その出力に含まれるコミットのみから PR 内容を生成してください。

### ステップ5: PR タイトルと本文の候補生成

**必ず3つの候補を生成**し、以下の構造で作成:

#### 候補1: 詳細版（推奨）

**タイトル**:
- 形式: `<主要な変更の詳細な説明>`
- 例: `新機能Aを実装しユーザー体験を向上`
- 長さ: 50-72文字程度

**本文**:
```markdown
## 📝 概要
<変更の目的と背景を2-3文で説明>

## ✨ 変更内容
- <主要な変更点1>
- <主要な変更点2>
- <主要な変更点3>

## 🎯 影響範囲

| Cohort / File(s) | 変更概要 |
|-----------------|---------|
| <カテゴリ名1><br>`<ファイルパス1>` | <変更内容の詳細な説明1> |
| <カテゴリ名2><br>`<ファイルパス2>`<br>`<ファイルパス3>` | <変更内容の詳細な説明2> |
| <カテゴリ名3><br>`<ファイルパス4>` | <変更内容の詳細な説明3> |

**変更統計**:
- 変更ファイル数: X件
- コミット数: Y件
- 追加: +N行
- 削除: -M行

## 🔗 関連情報
<関連する issue や参考資料があれば記載>

## ✅ テスト
<実施したテストや確認事項>
```

**影響範囲テーブルの生成ルール**:

1. **カテゴリ（Cohort）の決定**:
    - ファイルパスとコミットメッセージから関連する変更をグループ化
    - 意味のあるカテゴリ名を付ける（例: "インターフェース抽出", "実装クラスの更新", "DI設定の更新"）

2. **ファイルの記載**:
    - カテゴリ名の後に改行（`<br>`）を入れる
    - ファイルパスはバッククォートで囲む
    - **重要**: バッククォーテーションをバックスラッシュでエスケープしない
        - ✅ 正しい: `src/Module/FeatureA.php`
        - ❌ 間違い: \`src/Module/FeatureA.php\`
    - 複数ファイルがある場合は改行で区切る

3. **変更概要の記載**:
    - コミットメッセージから主要な変更内容を抽出
    - 技術的な詳細を含める（クラス名、メソッド名、依存関係など）
    - 変更の目的や影響を説明
    - 2-4文程度の説明文にする

4. **テーブル形式の注意点**:
    - 各セルは `|` で区切る
    - ヘッダー行の下に区切り線 `|---|---|` を入れる
    - セル内の改行は `<br>` タグを使用

**変更概要の生成例**:

**例1: インターフェース抽出（PHP）**
```markdown
| インターフェース抽出<br>`src/EmbedInterceptorInterface.php` | 既存のインターセプター機能を抽象化する新しいインターフェースを追加。異なる実装を依存性注入で切り替え可能にするための契約を提供。 |
```

**例2: 認証機能の実装（TypeScript/React）**
```markdown
| 認証コンポーネントの実装<br>`src/components/LoginForm.tsx`<br>`src/components/SignupForm.tsx` | ユーザー認証用のログインとサインアップフォームコンポーネントを実装。バリデーション、エラーハンドリング、ローディング状態の管理を含む。 |
| 認証フック<br>`src/hooks/useAuth.ts` | 認証状態管理のためのカスタムフックを追加。ログイン、ログアウト、トークン管理の機能を提供。 |
```

**例3: API エンドポイントの追加（Python/FastAPI）**
```markdown
| ユーザーAPI実装<br>`app/api/v1/endpoints/users.py`<br>`app/schemas/user.py` | ユーザー管理用のREST APIエンドポイントを実装。CRUD操作、バリデーション、認可チェックを含む。Pydanticスキーマで入出力を定義。 |
```

**例4: データベーススキーマの更新（Go）**
```markdown
| マイグレーション追加<br>`migrations/000003_add_user_preferences.up.sql`<br>`migrations/000003_add_user_preferences.down.sql` | ユーザー設定を保存するための新しいテーブルを追加。外部キー制約とインデックスを設定。 |
| リポジトリの更新<br>`internal/repository/user_repository.go` | ユーザー設定のCRUD操作をサポートするようリポジトリを拡張。トランザクション処理とエラーハンドリングを含む。 |
```

**例5: CI/CDパイプラインの改善**
```markdown
| GitHub Actions ワークフローの最適化<br>`.github/workflows/ci.yml` | テストとビルドの並列実行を導入し、CI時間を50%短縮。キャッシュ戦略を改善し、依存関係のインストール時間を削減。 |
```

**例6: フロントエンドのスタイリング**
```markdown
| レスポンシブデザイン対応<br>`public/css/main.css`<br>`public/css/responsive.css` | モバイル、タブレット、デスクトップに対応したレスポンシブスタイルを実装。ブレークポイント管理とフレックスボックスレイアウトを使用。 |
```

**カテゴリ名の決定のコツ**:
- ファイルパスのディレクトリ構造を参考にする
    - `src/components/auth/*` → 「認証コンポーネント」
    - `app/api/v1/endpoints/*` → 「APIエンドポイント」
    - `migrations/*` → 「データベースマイグレーション」
- コミットメッセージから変更の目的を抽出
    - "feat: add user authentication" → 「ユーザー認証機能の追加」
    - "refactor: extract interface" → 「インターフェース抽出」
    - "fix: resolve memory leak" → 「メモリリーク修正」
- 変更の性質を反映した名前を付ける
    - 追加系: 「〜の実装」「〜の追加」
    - 更新系: 「〜の更新」「〜の改善」
    - 削除系: 「〜の削除」「〜のクリーンアップ」

#### 候補2: 標準版

**タイトル**:
- 形式: `<変更の要約>`
- 例: `新機能Aを実装`
- 長さ: 30-50文字程度

**本文**:
```markdown
## ✨ 変更内容
- <主要な変更点1>
- <主要な変更点2>

## 🎯 影響範囲

| Cohort / File(s) | 変更概要 |
|-----------------|---------|
| <カテゴリ名1><br>`<ファイルパス1>` | <簡潔な変更説明1> |
| <カテゴリ名2><br>`<ファイルパス2>` | <簡潔な変更説明2> |

🎯 変更ファイル数: X件、コミット数: Y件
```

#### 候補3: 簡潔版

**タイトル**:
- 形式: `<変更内容>`
- 例: `機能A追加`
- 長さ: 20-40文字程度

**本文**:
```markdown
📝 <変更の概要を1-2文で説明>

🎯 変更ファイル数: X件、コミット数: Y件
```

**フォーマット規則**（全候補に適用）:
- **内容の情報源**: ステップ3で取得した `COMMITS` / `FILES` 区画の出力のみを使用
    - Context や直近のコミットは参照しない
- タイトルとボディのメッセージは日本語
- タイトルは72文字以内を推奨
- 本文は Markdown 形式
- **ファイル名を記載する場合**:
    - **`git diff` の出力をそのまま使用**（プロジェクトルートからの相対パス）
    - **行番号（`:1` など）は絶対に付けない**
    - バッククォーテーション `` ` `` で囲む
    - **🚨 重要**: バッククォーテーションの前後にバックスラッシュを**絶対に付けない**
        - ✅ 正しい: `src/Module/FeatureA.php`
        - ❌ 間違い: \`src/Module/FeatureA.php\`
    - **テーブル内でも同様**: バックスラッシュでエスケープしない（GitHub Markdown では不要）
- 英語と日本語の間に半角スペースを入れる

### ステップ6: PR 内容の選択

`AskUserQuestion` ツールで以下のように提示:

- `question`: "PR のタイトルと本文を選択してください"
- `header`: "Pull Request"
- `multiSelect`: `false`
- `options`: 3つの候補を配列で指定
    - 各 `label` には生成した PR タイトルを設定
    - 各 `description` には候補の特徴（「詳細版（推奨）」「標準版」「簡潔版」）と本文のプレビュー（最初の1-2行）を表示

### ステップ7: PR の作成または更新

1. **新規 PR の作成**（ステップ3で既存 PR がなかった場合）:

   **デフォルトで Draft PR として作成**:
   ```bash
   gh pr create --base <選択されたベースブランチ> \
                --title "<選択されたタイトル>" \
                --body "<選択された本文>" \
                --draft
   ```

   Draft PR として作成することで、レビュー前に内容を確認・調整できます。

2. **既存 PR のメタデータ更新**（ステップ3で「タイトル・本文を編集する」を選択した場合）:
   ```bash
   gh pr edit <PR番号> \
              --title "<選択されたタイトル>" \
              --body "<選択された本文>"
   ```

3. **オプション追加（必要に応じて）**:
    - レビュワーを指定する場合: `--reviewer <username>` を追加
    - ラベルを追加する場合: `--label <label-name>` を追加
    - マイルストーンを設定する場合: `--milestone <milestone-name>` を追加

4. **エラーハンドリング**:
    - PR 作成/更新に失敗した場合:
        - エラー内容をユーザーに報告
        - 一般的なエラー原因を提示:
            - 既に同じブランチで PR が存在する（ステップ3でチェック済みだが念のため）
            - リモートブランチが最新でない
            - 権限不足
            - ネットワークエラー
    - エラー解決のための提案を提示

5. **成功時の確認**:
    - 新規作成の場合: `gh pr create` 自身の出力から PR の URL を読み取る（`gh pr view` の追加実行は不要）
        - 「Draft PR が正常に作成されました」と日本語で報告
    - 更新の場合: `EXISTING_PR` 区画で取得済みの `url` を表示する
        - 「PR #<番号> のタイトルと本文を更新しました」と日本語で報告

    - PR の URL を表示
    - 「Ready にする場合は `gh pr ready <PR番号>`、レビュワーを追加する場合は `gh pr edit <PR番号> --add-reviewer <username>`、ラベルを追加する場合は `gh pr edit <PR番号> --add-label <label-name>` を実行してください」と案内

## 重要な制約

- **全てのレスポンスを日本語で行う**（分析結果、候補の説明、エラーメッセージ、成功報告など）
- **必ず3つの PR 候補を生成**（それ以上でもそれ以下でもない）
- **詳細版を1番目（推奨）に配置**する
- **詳細版には必ず CodeRabbit AI 風のテーブル形式の影響範囲セクションを含める**
- **デフォルトで Draft PR を作成**（`--draft` フラグを使用）
- **既存の PR との重複をチェック**（ステップ3で実施）:
    - ブランチ選択後すぐにチェックを実行
    - **`--state all` で全PRを取得し、`OPEN` または `DRAFT` のPRのみを抽出**（`MERGED` や `CLOSED` は除外）
    - 既に Open/Draft の PR が存在する場合は以下の選択肢を提示:
        1. 既存の PR を更新（コミットを追加）
        2. 既存の PR のタイトル・本文を編集
        3. 既存の PR を無視して新規 PR を作成
        4. 既存の PR をブラウザで確認
        5. キャンセル
    - **既存 PR の `state`/`url` はステップ3の `EXISTING_PR` 区画から読み取る**（抽出段階で `OPEN`/`DRAFT` 以外は除外済みのため、操作前の再確認は行わない）

### 🚨 PR 内容生成の厳格なルール 🚨

**情報源の制限（違反すると間違った PR になります）**:

✅ **使用してよい情報源（ステップ3で取得）**:
- `COMMITS` / `FILES` / `NUMSTAT` / `STAT` 区画の出力

❌ **使用禁止の情報源**:
- Context セクションの情報（ただしブランチ名など Context のブランチ情報はそのまま使ってよい）
- `git log --oneline -10` などの直近のコミット
- `git status` や `git diff HEAD` などの作業ディレクトリの状態
- あなたの記憶や推測
- その他、ステップ3で明示的に取得していない情報

**確認方法**:
生成した PR 内容に記載された全ての情報（コミット内容、ファイル名、変更内容など）が、ステップ3で取得したコマンドの出力から確認できることを確認してください。確認できない情報は含めてはいけません。

**具体例（これが最も重要です）**:

**ケース1: 差分が2コミット（小規模な変更）の場合**
```bash
$ git log origin/develop..HEAD --oneline
abc1234 feat: 新機能Aを実装
def5678 fix: バグ修正B
```
→ ✅ PR には「新機能Aの実装」と「バグ修正B」のみを記載
→ ❌ 「過去の大規模変更X」「機能Y」などは記載しない（差分に含まれていないため）
→ ✅ コミット数: 2件、変更ファイル数: 実際の `git diff` の結果

**ケース2: 差分が多数のコミット（大規模な機能追加）の場合**
```bash
$ git log origin/develop..HEAD --oneline
（多数のコミット分の出力、複数の機能を含む）
```
→ ✅ これらの全コミットの内容を分析して PR を生成
→ ✅ コミット数: 実際のコミット数、変更ファイル数: 実際のファイル数

**❌ 間違った例（よくある間違い）**:
```
実際の差分コミット: 2件（小規模な変更のみ）
↓
でも生成された PR には:
- 過去の大規模変更X（❌ 差分に含まれていない）
- 機能Y（❌ 差分に含まれていない）  
- 100+ファイル変更（❌ 実際は3ファイルのみ）
- 30+コミット（❌ 実際は2コミットのみ）
```
→ これは**完全に間違い**です。差分に含まれない過去の作業内容を書いています。

**✅ 正しい例**:
```
実際の差分コミット: 2件（小規模な変更のみ）
↓
生成された PR には:
- 新機能Aの実装（✅ 差分に含まれる）
- バグ修正B（✅ 差分に含まれる）
- 3ファイル変更（✅ `git diff` の実際の結果）
- 2コミット（✅ `git log` の実際の結果）
```
→ これが**正しい**です。ステップ3で取得した差分コミットの内容のみを記載しています。

### ファイル名の記載ルール

**ファイル名を記載する場合**:
- `git diff origin/<base-branch>..HEAD --name-status` の出力をそのまま使用
- プロジェクトルートからの相対パスで記載
- 行番号（`:1` など）は**絶対に付けない**
- バッククォーテーション `` ` `` で囲む
- **🚨 最重要**: バックスラッシュによるエスケープは**絶対に行わない**
    - これは通常のテキストでもテーブル内でも同じ
    - GitHub Markdown では、テーブル内のバッククォーテーションをエスケープする必要はない

**例**:
- ✅ 正しい: `src/Module/FeatureA.php`
- ❌ 間違い: `Module/FeatureA.php`（パスが不完全）
- ❌ 間違い: `FeatureA.php`（パスが不完全）
- ❌ 間違い: `src/Module/FeatureA.php:1`（行番号が付いている）
- ❌ 間違い: \`src/Module/FeatureA.php\`（バッククォーテーションの前にバックスラッシュが付いている）

**テーブル内での使用例**:
```markdown
| Cohort / File(s) | 変更概要 |
|-----------------|---------|
| 機能実装<br>`src/Module/FeatureA.php` | 機能Aの実装... |
```
↑ この形式が正しい（バックスラッシュなし）

```markdown
| Cohort / File(s) | 変更概要 |
|-----------------|---------|
| 機能実装<br>\`src/Module/FeatureA.php\` | 機能Aの実装... |
```
↑ この形式は**間違い**（バックスラッシュが付いている）

### その他の制約

- **コミットが存在しない場合**:
    - 「ベースブランチとの差分がありません。変更をコミットしてから PR を作成してください」と通知して終了
- **gh CLI が利用できない場合**:
    - 「gh CLI がインストールされていません。https://cli.github.com/ からインストールしてください」と通知して終了

## Tips

- **複数の変更種別が混在する場合**:
    - 最も重要な変更の種別を type として使用
    - 本文で各種別の変更を分けて説明

- **Breaking Changes がある場合**:
    - タイトルに⚡️を追加: `⚡️API 仕様を変更`
    - 本文に `## ⚠️ Breaking Changes` セクションを追加

- **Issue 番号を含める場合**:
    - 本文の最後に `Closes #123` または `Fixes #456` を追加
    - GitHub が自動的に Issue とリンク

- **Draft PR から Ready にする場合**:
    - PR 作成後に `gh pr ready` コマンドを実行
    - または、GitHub の Web UI から "Ready for review" ボタンをクリック

- **テーブル形式の変更概要を効果的に書くコツ**:
    - 各カテゴリの変更が何を達成するかを明確に記述
    - 技術的な詳細（クラス名、関数名、モジュール名、使用技術）を含める
    - 変更の理由や背景を簡潔に説明
    - 他の変更への影響や依存関係を記載
    - プロジェクト固有の用語を使用してOK（むしろ推奨）
    - 2-4文程度で簡潔にまとめる

- **ファイル名のフォーマット（重要）**:
    - ファイル名はバッククォーテーション `` ` `` で囲む
    - **バックスラッシュによるエスケープは不要**（GitHub Markdown ではテーブル内でもエスケープ不要）
    - 正しい例: `src/Module/FeatureA.php`
    - 間違った例: \`src/Module/FeatureA.php\`（バックスラッシュが付いている）

- **カテゴリ化の実践例**:
    - **ディレクトリ構造を活用**: `src/components/auth/*` → 「認証コンポーネント」
    - **機能単位でグループ化**: ログイン関連ファイルをまとめて「ログイン機能の実装」
    - **技術スタック別**: フロントエンド、バックエンド、データベース、インフラなど
    - **変更の性質別**: 新機能追加、バグ修正、リファクタリング、パフォーマンス改善など
